# Test fixtures

`synthetic.jfr` is a small (~250 KB) **synthetic but real** JDK Flight
Recording generated by [`GenerateRecording.java`](GenerateRecording.java) with
`jdk.jfr`. It exists so the test suites run without downloading the
multi-hundred-MB recordings that used to live on Dropbox. It is
single-producer (no datadog-style type-ID remapping between chunks) and
contains hundreds of `jdk.ExecutionSample` events with stack traces,
allocation samples and GC events, which is all the parser and shell tests
need.

The recording is deliberately scrubbed of host-identifying data because it is
committed to the repository: `jdk.InitialEnvironmentVariable`, `jdk.SystemProcess`
and `jdk.NativeLibrary` are disabled, and the `java.home` /
`java.library.path` values point at generic system locations rather than the
machine that generated the file. If you regenerate it, keep it that way:

```bash
# Use a system JDK (not a per-user one like sdkman) and override the
# library path, so the embedded InitialSystemProperty paths stay generic:
JH=/Library/Java/JavaVirtualMachines/jdk-17.jdk/Contents/Home   # adjust for your machine
"$JH/bin/java" -Djava.library.path=/Library/Java/Extensions test-fixtures/GenerateRecording.java test-fixtures/synthetic.jfr
```

After regenerating, check the result before committing:

```bash
strings test-fixtures/synthetic.jfr | grep -E '/Users/|/home/'   # must print nothing
```

Tests rely on `jdk.ExecutionSample` events with non-empty stacks and
`startTime`; anything richer is best effort. A fresh fixture is not expected
to be byte-identical to the committed one (timestamps, addresses); nothing
pins the bytes.

This is deliberately **not** a substitute for the real-world recordings when
measuring performance. Benchmarks want `./get_resources.sh --full`, which
downloads the original Dropbox recordings (`test-ap.jfr` ~170 MB,
`test-jfr.jfr` ~1.7 GB) into the same locations.

The `test-dd.jfr` slot is filled by the checked-in Datadog recording
`jfr-shell-tck/src/main/resources/tck-test.jfr` instead, because the jfr-mcp
integration tests and the go-parser tests expect a Datadog-flavoured
recording. See `get_resources.sh`.
